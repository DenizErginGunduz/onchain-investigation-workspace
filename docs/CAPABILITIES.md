# Capability status

| Capability | Status and boundary |
| --- | --- |
| Graph, ledger, saved cases and notes | Implemented; local single user |
| One-click evidence demo | Implemented; creates a synthetic local case |
| Portable snapshots | Implemented; equivalent format does not mean equivalent intelligence |
| Polymarket adapter | Experimental; one page, at most 50 rows |
| Receipt corroboration | Implemented; one to three selected transactions per bundle |
| Offline replay | Implemented; self-consistency is not authenticity |
| Purchase/fee interpretation | One narrow supported pattern |
| Collateral tracing | Fixed window/asset/recipient; no verified second hop |
| Real validation | One bounded wallet case, three similar selected transactions |
| Full API-versus-chain benchmark | Proposed; no incremental-value result |
| AML/fraud/insider detection | Not implemented |
| PnL, skill persistence, rankings | Not implemented |
| Sanctions, service labels, clustering | Not implemented |
| Bridge resolver / multichain tracking | Not implemented |
| Enterprise hosting and authentication | Not implemented |

## Next validation gate

The next technical question is whether chain reconstruction contributes material, reliable information beyond the complete official API response. A future stratified API-versus-chain study would measure agreement, missing fields, unresolved rows and review cost before broader collection or detection features are considered.

No wallet-skill, detector-accuracy or commercial-readiness result is claimed.
